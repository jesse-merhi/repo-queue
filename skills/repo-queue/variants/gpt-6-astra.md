---
name: repo-queue
description: Coordinate authorized GitHub native queues and local GitHub or Bitbucket PR turns while retaining the original owner.
---

Use `repo-queue` for authorized GitHub or Bitbucket Cloud PR merges on this machine, including requests to merge, land or ship a PR. A request to implement or review alone does not authorize merging or require a turn. GitHub native queues own merge order and combined validation; RepoQ retains the original owner for repairs. Repositories without a native queue use local repository turns. The repository workflow retains its technical review, security and validation gates.

When the user explicitly directs a named PR or stack into RepoQ, record that instruction in the checkpoint. It authorizes the ordinary work needed to finish those PRs: review, required CI including paid jobs, routine repairs, justified recovery after diagnosis, and merge once technical gates pass. Do not ask again for a `+1` reaction, routine CI spending approval, or merge confirmation for that scope. Diagnose failed CI and verify repairs locally before a justified rerun; a failure alone is not a reason to repeat paid jobs. Ask when the scope, CI inputs or spending changes materially or a technical blocker needs a user decision. An entry added without that user instruction, queue status, or wake message does not grant this authority; use only the authorization already present in the originating task. Never add a reaction on the user's behalf.

For a native submission, finish the required code review, security checks, local proof and PR-head CI before running `submit`. For a stack, complete those gates on every current head through the selected PR. Record the reviewed heads and passing evidence in a checkpoint outside the checkout using [continuation guidance](references/continuation.md), then re-read the heads before submitting. If a head changed, complete the affected review and checks first. The native happy path proceeds automatically and never wakes the owner to perform unfinished preparation.

Register the prepared candidate from its original harness, conversation UUID and worktree. `--authorize-merge` records the explicit authority already supplied by the user; it does not create authority:

```sh
repo-queue start
repo-queue submit <pr-url> --authorize-merge --agent <codex-or-claude> --task <conversation-uuid> --cwd <worktree> \
  --checkpoint <absolute-checkpoint-file>
```

For an authorized GitHub stack prefix, add `--stack` only when the user authorized all lower unmerged PRs through the selected PR. GitHub queues that prefix through its stack-aware API. RepoQ records the scope and heads and queries the native queue for the actual target branch, including classic protection and rulesets. A capability read error blocks registration instead of selecting a local merge. Bitbucket and GitHub targets with no native queue use the legacy local turn described below. Existing registrations keep their original mode and owner.

When the returned entry includes `native`, save its entry, token and authorization, then end the turn. The runtime observes the provider without model polling. `admission_pending` is not queue membership; `enqueued` and `validating` come from provider evidence. A repair wake identifies an admission failure or ejection and grants no repository-wide lock. Claim or verify the repair turn using the commands below, diagnose and repair the cause, complete the affected technical gates, then run `repo-queue resume-native <entry-id> --token=<token>`. Save its replacement token and end the turn. Do not acquire a local repository turn or merge directly. An uncertain submission requires remote reconciliation before `resume-native --quiescent`; never blindly enqueue twice. `block` retains repair ownership but does not block unrelated PRs. Only provider-confirmed merge marks a native entry done. Completion is visible in `status`; repair wakes follow the ordinary delivery safeguards.

For legacy local work, acquire the repository turn before the final target-branch update and merge-validation run. Ordinary development and tests may happen first. Save a checkpoint identifying the current candidate, existing review evidence or pending impact assessment, running jobs and next action; pending preparation is allowed in this legacy checkpoint because registration schedules an owner turn rather than submitting to GitHub:

```sh
repo-queue start
repo-queue add <pr-url> --agent <codex-or-claude> --task <conversation-uuid> --cwd <worktree> \
  --checkpoint <absolute-checkpoint-file>
```

RepoQ records the original harness's configuration directory, including a custom `CODEX_HOME` or `CLAUDE_CONFIG_DIR`. Keep the checkpoint current after integration, review, validation and interruption. An unfinished native prefix cannot be registered as legacy work, or vice versa; preserve its original owner.

Use the harness-provided identity. For Codex CLI, `CODEX_THREAD_ID` may supply it; in the desktop use the current task identity. For Claude, use the session UUID provided by the session interface or `claude agents --json`. Never substitute another task or create a new conversation to receive the turn. If the identity cannot be established, ask for it. For a Codex desktop owner on macOS using the default `CODEX_HOME`, add `--desktop` when registering. This opts in to loading that exact desktop task after native queue acceptance. Omit it for CLI owners, custom `CODEX_HOME`, and other agents. A successful activation request is not a claim.

If registration returns `waiting` or `reserved`, save the returned entry ID and token in the conversation, then end the turn completely. If it returns `claimed` or `blocked`, this conversation already owns an unfinished turn: inspect that work and use the recovery guidance below instead of registering or claiming again. If it returns `done`, the recorded turn is complete; do not start another merge from that entry. Do not poll or hold a tool call. Codex desktop must remain running for `codex queue` delivery. A running local Claude Code session can remain open. RepoQ uses a restricted native sender to message the exact original session; this adds a sender model turn and retains the normal configured permission mode. If the owner session has exited, RepoQ uses `claude -p --resume` in its original directory. Native send success means accepted, not necessarily delivered: Claude can hold or refuse messages under its inbound controls, including per-session mode differences. The successful queue claim establishes that the owner acted. Inspect the original session's notices and report the concrete cause when available; never retry repeatedly, change permission settings, terminate your process or fork a receiver to force delivery. Desktop Code is eligible when it exposes a compatible local Claude Code inbox. General Claude Chat/Cowork and remote/cloud sessions are separate surfaces.

On the first wake, run its exact `claim` command before merge work and retain the successful result in the task checkpoint. A claim succeeds only once. After compaction, a resumed turn, or a repeated wake, do not claim an already-owned entry again. Confirm the existing claim using the current conversation's actual identity and original worktree:

```sh
repo-queue verify-claim <entry-id> --token=<token> \
  --agent <codex-or-claude> --task <current-conversation-uuid> --cwd <original-worktree>
```

This read-only check succeeds only for the matching owner, token and claimed state. Success permits continuing that existing workflow from its saved checkpoint, after accounting for any jobs already running. It grants no second claim or parallel owner. If a claim fails, inspect the recorded state: an existing claim for this conversation with the same token needs verification. A stale token or different owner grants no turn; do not copy a replacement token from status to make an old wake succeed. A waiting entry has no turn. Only the current reservation and its replacement wake permit a fresh claim. Ignore a duplicate notification without abandoning another verified turn already in progress. For blocked work, resolve the blocker and use recovery below; do not treat verification as an unblock command. Complete the existing authorized repository workflow and report any required approval.

After a successful claim or verification, read the returned `checkpoint_path` and follow the continuation guidance before dispatching more work. An older entry without a checkpoint continues from its original conversation.

For a legacy local turn, after the workflow succeeds and associated remote work has finished, run the wake message's `done` command. For native repair, use `resume-native` after completing the affected gates and let the runtime confirm merge; `done` cannot stand in for provider evidence. If blocked, run its `block` command with a concrete reason, explain what is needed and end the turn. A blocked legacy entry retains the repository reservation; a native entry retains only its repair owner.

For delivery failure before claim, inspect `repo-queue status` and use `retry <id> --token=<token>` after resolving the cause. Retry returns a replacement token. If the owner was interrupted after claim or blocked, establish that the old owner and its remote jobs have stopped before `recover <id> --token=<token> --quiescent`. This also applies when this conversation returns to its own blocked entry after its blocker is resolved: first confirm the previous workflow and remote jobs have stopped. Recovery invalidates the old token and sends a new wake. After retry or recovery, save the replacement entry/token and end the turn; wait for that wake instead of claiming immediately. Never claim twice, release a turn because time passed, or report completion while remote work may still be running.

If a delivery slot remains orphaned after a dispatcher crash, inspect status and establish that the original agent process and its work have stopped before using `repo-queue reconcile-delivery <entry-id> --token=<current-token> --quiescent` for your entry. This only clears delivery accounting; it preserves queue state, token and reservation, including for completed work. It neither sends a wake nor grants a claim. Use the separate retry or recovery flow only if a notification is still needed; never clear accounting merely because delivery is slow.

For an unclaimable reserved GitHub entry whose PR is already merged, first confirm the original owner and its remote work have stopped, and clear any orphaned delivery slot as above. The CLI cannot inspect an active model turn; `--quiescent` is your assertion based on the original task and process state. Only after a failed or uncertain notification, use `repo-queue complete-merged <entry-id> --token=<current-token> --quiescent --reason <reason>` for an entry you are authorized to manage. It verifies the exact remote merge, refuses an active delivery or owner claim, and records an audit reason before completing the turn. Never use it for an open PR, a merely slow wake, or unresolved owner activity.
